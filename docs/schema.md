# Миграции схемы

`tnt-schema` держит схему спейсов под номером версии: в базе хранится
номер, в коде — пронумерованные шаги, и раннер догоняет базу до кода.
Шаг и запись новой версии идут одной транзакцией, поэтому изменение
либо применено целиком, либо не применено вовсе.

```lua
local schema = require('tnt.schema')

schema.register(1, function(box)
    box.schema.space.create('orders', {
        format = { { name = 'id', type = 'unsigned' } },
    }):create_index('primary')
end)

assert(schema.upgrade())
```

Отката нет: DDL уезжает на реплики журналом, и понижение версии
отвергается. Пропуск в нумерации, версия в базе новее кода, инстанс
только для чтения — отказ до первого шага, а не посреди подъёма.
Что применено, когда и каким узлом, отвечает `schema.status()`.

## Зачем пакет

Схема спейсов меняется вместе с кодом, а живёт в базе, и после каждой
выкатки код должен знать, что из его изменений уже применено. `box.once`
для этого мал: он умеет только «выполнить один раз под ключом» и не знает
ни версии, ни порядка шагов, ни того, что DDL допустим лишь там, где
разрешена запись. Пакет делает четыре вещи:

- **Версия и шаг — одна транзакция.** Падение между изменением схемы
  и записью версии оставило бы схему новой, а версию старой, и следующий
  запуск применил бы шаг повторно. Здесь шаг и `replace` версии идут
  под одним `box.begin`/`box.commit`: упавший шаг откатывается целиком,
  версия остаётся прежней.
- **Порядок и полнота проверяются до первого шага.** План строится
  от версии в базе до версии в коде, и пропущенный номер, понижение,
  инстанс только для чтения — отказ, пока схема ещё не тронута. Половина
  применённых шагов хуже, чем ни одного: её не повторить и не откатить.
- **Шагу достаётся весь срез файбера.** Шаг идёт в транзакции и уступать
  не может, а ядро обрывает работу без уступки после секунды. Раннер
  уступает перед шагом и после него — срез начинается заново и не
  достаётся вызывающему, — а долгому шагу срез задают при регистрации.
- **Журнал шагов.** Версия говорит, докуда поднята схема, но не когда
  и кем, — а после выкатки на десяток узлов оператор спрашивает именно
  это. В той же транзакции, что шаг и версия, ложится запись журнала:
  номер, стенное время, имя применившего узла и длительность шага.
  `status()` сводит версию, журнал и шаги кода в одну картину.

Зависимости — `tnt-must` (проверка настроек шага) и `tnt-external`
(подмена уступки, часов и имени узла в проверках).

## Как пользоваться

### Объявить шаг: `register`

```lua
local schema = require('tnt.schema')

schema.register(1, function(box)
    local orders = box.schema.space.create('orders', {
        format = {
            { name = 'id', type = 'unsigned' },
            { name = 'status', type = 'string' },
        },
    })
    orders:create_index('primary', { parts = { { field = 'id', type = 'unsigned' } } })
end)

schema.register(2, function(box)
    box.space.orders:create_index('by_status', {
        parts = { { field = 'status', type = 'string' } },
        unique = false,
    })
end)
```

`register(version, step, opts)` кладёт шаг в реестр. `version` —
натуральное число, и каждый номер регистрируется один раз; `step` —
функция, которая получает `box` и меняет схему; всё, что она делает,
идёт в одной транзакции с записью версии. Номер шага — это версия,
до которой он поднимает схему: шаг 1 поднимает с нулевой до первой.
Порядок регистрации не важен, порядок применения — по номерам.

Неправильный аргумент — ошибка программиста, и `register` бросает:

```lua
schema.register(0, function() end)
--> версия шага должна быть натуральным числом
schema.register(1, 'не функция')
--> шаг 1 должен быть функцией
schema.register(1, function() end)
--> шаг 1 уже зарегистрирован
schema.register(3, function() end, { slice = 0 })
--> настройки шага.slice — число больше 0, а не 0
schema.register(3, function() end, { slyce = 30 })
--> настройки шага: ключа «slyce» нет, есть slice
```

Шаг обязан быть совместим с предыдущей версией кода. Инстансы
обновляются по одному, и схема после шага N какое-то время читается
кодом версии N-1: переименованное поле или удалённый индекс сломают
последовательную выкатку на первом же инстансе. Опасное изменение
делается двумя выкатками: сначала добавить новое рядом со старым,
потом, когда старым никто не пользуется, убрать его.

### Поднять схему: `upgrade`

```lua
local report, err = schema.upgrade()
```

Раннер читает версию из базы, строит план до наибольшей
зарегистрированной и применяет шаги по одному, каждый — в своей
транзакции с записью версии. Отчёт — таблица:

```lua
report.from        --> 0        версия в базе до подъёма
report.to          --> 2        версия в коде
report.applied     --> { 1, 2 } применённые шаги по порядку
report.elapsed_ms  --> 3.4      время подъёма по монотонным часам
```

Повторный вызов ничего не применяет: `applied` пустой, `elapsed_ms`
нулевой, в журнале тишина. Так раннер зовётся при каждом старте
и при каждом получении лидерства, а не «когда есть новые шаги».

Отказ — пара `nil, err`, и схема при нём остаётся ровно в том виде,
в каком её застал отказ:

| Отказ | Когда |
|---|---|
| `менять схему нельзя: …` | `box` не настроен или инстанс только для чтения; причину называет ядро (`box.info.ro_reason`) |
| `в базе версия 3, а в коде 2: понижение версии недопустимо` | инстанс запущен кодом старее базы |
| `шаг 2 не зарегистрирован` | пропуск в нумерации; ни один шаг не применён |
| `шаг 2 не применён: …` | шаг бросил; его транзакция откачена, версия прежняя, шаги после него не тронуты |
| `шаг 2 не применён: пока раннер стоял на уступке, версия в базе стала 2 — миграции применяет кто-то ещё` | сосед поднял схему за время уступки |

Отказ на реплике — отказ, а не исключение: раннер безопасно звать
на любом узле, и там, где записи нет, он просто скажет об этом. Схему
поднимает лидер, а реплики получают её журналом вместе с версией.

Вызов внутри транзакции — исключение: раннер уступает управление
вокруг шага, а уступка обрывает транзакцию вызывающего. Это ошибка
программиста, и место в сообщении — строка вызывающего:

```lua
box.begin()
schema.upgrade()
--> раннер миграций уступает управление вокруг шага и этим обрывает транзакцию: внутри транзакции его не зовут
```

### Долгий шаг: `slice`

```lua
schema.register(3, function(box)
    for _, order in box.space.orders:pairs() do
        box.space.orders:replace(order:update({ { '=', 'status', 'new' } }))
    end
end, { slice = 30 })
```

Шаг идёт в транзакции, а уступка внутри транзакции memtx обрывает её
(с `memtx_use_mvcc_engine` уступку переживает только DML, DDL — нет).
Поэтому шаг не уступает, и единственный его предел — срез файбера: ядро
сверяет его на обращениях к `box` раз в тысячу и после секунды работы
без уступки обрывает шаг ошибкой `fiber slice is exceeded`. На Tarantool
3.8 это около 250 000 `replace` в одной транзакции; транзакция
откатывается, версия остаётся прежней, а отказ подсказывает задать срез.

`slice` — секунды, на которые шагу отдаётся файбер: это `fiber.set_slice`
на время шага, и срез живёт до первой уступки, то есть ровно до конца
шага. Вызывающему после шага он не достаётся. Цена названа вслух: пока
шаг идёт, на узле не работает ни один другой файбер — ни репликация,
ни запросы, — а реплики получают одну транзакцию на все строки.

Раннер отдаёт срез шагу целиком и без `slice`: перед шагом файбер
уступает, и срез начинается заново — иначе шагу достался бы остаток
после работы вызывающего. После шага уступает снова: ни съеденный шагом
срез, ни выданный ему сверх обычного вызывающему не достаются.

### Где лежит версия: `configure`, `current_version`, `target_version`

```lua
schema.configure({ meta_space = 'app_versions', steps_space = 'app_version_steps' })

schema.meta_space_name()   --> 'app_versions'
schema.steps_space_name()  --> 'app_version_steps'
schema.current_version()   --> 0, пока спейса нет
schema.target_version()    --> 3, наибольший зарегистрированный шаг

schema.configure({ meta_space = '' })
--> meta_space должен быть непустой строкой
```

Версия хранится в спейсе `app_schema_meta` в записи
`{ 'schema_version', '2' }`, журнал шагов — в спейсе `app_schema_steps`
записями `{ версия, когда, узел, мс }`; имена спейсов меняются через
`configure` до первого подъёма, непустая строка — иначе бросок со
строкой вызывающего. Оба спейса разворачивает сам раннер, и оба
реплицируемые: шаги выполняются на лидере, их результат уезжает
на реплики журналом, и версия должна уехать вместе с ним. Локальный
спейс оставил бы реплику с изменёнными данными и старой версией,
и она попыталась бы применить тот же шаг ещё раз; журнал на реплике
без записей не назвал бы ни времени, ни узла.

Ведущего подчёркивания в имени нет намеренно: оно зарезервировано
под системные спейсы.

### Журнал: `configure({ logger })`

```lua
local log = require('log')
local json = require('json')

schema.configure({
    logger = {
        info = function(message, fields) log.info('%s %s', message, json.encode(fields)) end,
        warn = function(message, fields) log.warn('%s %s', message, json.encode(fields)) end,
        error = function(message, fields) log.error('%s %s', message, json.encode(fields)) end,
    },
})
```

Пакет своего журнала не навязывает и по умолчанию молчит. `logger` —
таблица с `info`, `warn` и `error`, каждая берёт сообщение и таблицу
полей; журнал Tarantool сам по себе таблицу полей не печатает, поэтому
в примере она уходит строкой JSON:

| Сообщение | Уровень | Поля |
|---|---|---|
| `применение миграций` | `info` | `from`, `to`, `steps` |
| `шаг применён` | `info` | `version`, `elapsed_ms` |
| `шаг миграции не применён` | `error` | `version`, `err` |

Пустой план в журнал не пишется.

### Что применено: `status`

```lua
local status, err = schema.status()
--> {
-->     instance = 'storage-001-b',   -- кто ответил: версия и журнал — его
-->     current = 2,                  -- версия в базе
-->     target = 3,                   -- версия в коде
-->     steps = {
-->         { version = 1, applied = true, registered = true,
-->           applied_at = 1790382917.14, instance = 'storage-001-a', elapsed_ms = 1.9 },
-->         { version = 2, applied = true, registered = true },   -- применён до журнала
-->         { version = 3, applied = false, registered = true },  -- ждёт
-->     },
--> }
```

Применённым шаг считается по версии в базе — так же, как его считает
сам раннер; журнал добавляет, когда (`applied_at` — секунды эпохи
по стенным часам применившего узла), каким узлом (`instance` — имя
из конфигурации, а у узла без имени — uuid) и сколько миллисекунд шёл
шаг. Список идёт с первого шага до наибольшего из кода и журнала,
поэтому видны и пропуск в нумерации кода (`registered = false`
у неприменённого — подъём на нём откажет), и шаг, которого в коде уже
нет (`registered = false` у применённого — база новее кода).

Статус читает и там, где писать нельзя: на реплике видны шаги,
применённые лидером, с его именем в `instance`, а верхнее `instance` —
сама реплика. Спейсов раннера статус не разворачивает: на узле, где
подъёма не было, всё из кода просто ждёт. Без настроенного `box` —
отказ `состояние схемы не прочитать: box не инициализирован`.

Шаг, применённый раннером до журнала, виден применённым, но без
времени и узла: придумывать их пакет не берётся. Запись журнала выше
версии в базе не показывается — версию правили руками, и шаг
применится заново; его новая запись заменит старую.

### Можно ли менять схему: `can_run_ddl`

```lua
local allowed, reason = schema.can_run_ddl()
```

`true`, когда `box` настроен и разрешена запись; иначе `false` и
причина: «box не инициализирован», «box.info недоступен» либо
`box.info.ro_reason` ядра — «инстанс только для чтения», если ядро
причины не назвало. `upgrade` спрашивает то же самое перед подъёмом;
отдельно это нужно тому, кто решает, звать ли раннер на этом узле
вовсе.

### План без применения: `plan`

```lua
schema.plan(0, 2)   --> { 1, 2 }
schema.plan(2, 2)   --> {}
schema.plan(0, 4)   --> nil, 'шаг 4 не зарегистрирован'
schema.plan(2, 1)   --> nil, 'понижение версии с 2 до 1 недопустимо'
```

Список шагов от одной версии до другой — тот же, что строит `upgrade`.
Нужен, чтобы показать оператору, что применится, не применяя.

### Подмена в проверках: `_set_source`

Уступку, часы и имя узла раннер берёт через внешние зависимости,
и проверка подменяет их на модуле:

```lua
schema._set_source({
    yield = function() ... end,      -- вместо fiber.yield
    monotonic = function() ... end,  -- вместо clock.monotonic
    realtime = function() ... end,   -- вместо clock.realtime: время в журнале шагов
    instance = function() ... end,   -- вместо box.info.name, а без имени — box.info.uuid
})
schema._set_source(nil)              -- настоящие вернулись
```

Подменённая уступка — единственный способ встать ровно между чтением
версии и шагом и сделать там то, что делают соседние файберы: поднять
схему самой. Подменённые часы дают `elapsed_ms` точным числом; на
настоящих проверка сверяла бы только диапазон и пропускала ошибку
единиц или знака. Стенные часы и имя узла дают точную запись журнала.

## Чем пришлось поступиться

**Отката нет.** Шаг знает только дорогу вперёд. DDL уезжает на реплики
журналом, и «откатить» его на живом кластере значит выкатить ещё один
шаг вперёд — под следующим номером и совместимый с текущим кодом.
Понижение версии, на бумаге безобидное, отвергается по той же причине:
инстанс, запущенный старым кодом поверх новой базы, может не понять
данные.

**Реестр шагов один на процесс.** Шаги, имя спейса с версией и журнал —
состояние модуля, а не экземпляра: `register` из разных мест кладёт
в один реестр, и второе приложение в том же процессе своей схемы вести
не может. Так сделано намеренно: у процесса Tarantool одна база и одна
схема, а два реестра дали бы два спейса с версией и два расписания
подъёма для одних и тех же спейсов.

**Шаг не уступает, и узел стоит весь шаг.** Обход спейса кусками
с уступкой между ними шагу недоступен: уступка внутри транзакции memtx
обрывает её. Предел шага — срез файбера, и долгий шаг получает срез
в секундах ценой всего узла на это время. Шаг, которому нужны минуты,
не миграция: перенос данных такого размера делается фоновым обходом
кусками, а миграцией — только изменение схемы под него.

**Внутри транзакции раннер не зовут.** Уступка вокруг шага оборвала бы
транзакцию вызывающего молча, и он узнал бы об этом только на фиксации.
Поэтому это исключение, а не отказ парой: тот, кто позвал раннер
в транзакции, ошибся в коде, и вернуть ему отказ некому.

**Версия — на этом инстансе, и только на нём.** Раннер поднимает схему
там, где его позвали, и ничего не знает о соседних репликасетах. На
шардированном кластере схему поднимает лидер каждого репликасета
независимо; согласовать их версии между собой, заметить, что один
из них отстал, — дело того, кто зовёт раннер и читает
`current_version` с каждого.

**Испорченная версия читается как ноль.** Нечисловое значение в спейсе
с версией не роняет старт: раннер считает схему нулевой и строит план
с первого шага. Шаг, создающий уже существующий спейс, откажет,
и схема останется нетронутой, — а вот шаг, который только перекладывает
данные, применился бы повторно. Починить значение — дело оператора,
и пакет об этом не догадывается.

**Журнал шагов — стенное время узла.** `applied_at` берётся с часов
того узла, что применил шаг, и сравнивать записи разных узлов можно
с точностью до расхождения их часов. Длительность при этом честная —
она по монотонным часам, — а в журнал ложится длительность самого
шага: фиксация с уступкой после записи в неё уже не входит.

**Состояние — этого узла.** `status()` читает свои спейсы, как
и `current_version`: на шардированном кластере состояние у ведущего
каждого репликасета своё, и собрать их в одну картину — дело того,
кто спрашивает каждого. Роутер без спейсов раннера ответит, что всё
из кода ждёт, — спрашивать надо узел с данными.

**Отказ шага — строка, а не объект.** Текст отказа складывается
из номера шага и того, что шаг бросил: обёртка над `box.error` с полями
понадобилась бы одному вызывающему из многих, а строка читается
в журнале и сравнивается в проверке как есть. Срыв на срезе — единственный
отказ, который раннер узнаёт по типу ошибки ядра и снабжает подсказкой.

## Проверки

Проверки лежат в `test/` и идут на luatest; зовутся они через `make`,
который держит каталог узлов luatest своим. Реестр, план
и `can_run_ddl` проверяются без базы, с подменённым `box`; применение —
